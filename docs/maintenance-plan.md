# SWEBOK Maintenance Plan — QualityLab_1

## 1. Призначення

Цей документ описує правила супроводу системи QualityLab_1 після розгортання.

План визначає:

- рівні підтримки L1 / L2 / L3;
- правила ескалації;
- відомі проблеми;
- тимчасові обходи;
- пріоритети технічного вдосконалення;
- зв’язок із runbook та SLO.

## 2. Рівні підтримки

### L1 — First Line Support

L1 виконує первинну перевірку проблеми.

Основні дії:

- перевірити `/health`;
- перевірити `/api/system/info`;
- перевірити доступність сервісу;
- перевірити базові логи;
- використати відповідний runbook;
- визначити severity.

L1 не змінює код системи.

Якщо проблема не вирішена стандартними діями — звернення передається на L2.

### L2 — Technical Support

L2 виконує технічну діагностику.

Основні дії:

- аналіз application logs;
- аналіз external dependencies;
- перевірка конфігурації;
- перевірка API;
- перевірка retry / fallback;
- відтворення проблеми у тестовому середовищі;
- виконання rollback за runbook.

Якщо потрібна зміна коду або архітектури — проблема передається на L3.

### L3 — Engineering / Development

L3 виконує глибокий технічний аналіз.

Основні дії:

- аналіз коду;
- виправлення дефектів;
- зміна архітектури;
- зміна persistence або integration layer;
- оновлення automated tests;
- оновлення документації;
- створення RFC для значних змін;
- підготовка нового релізу.

## 3. Критерії ескалації

L1 → L2:

- runbook не вирішив проблему;
- помилка повторюється;
- сервіс працює у degraded mode;
- є проблема із зовнішньою залежністю;
- потрібен аналіз логів або конфігурації.

L2 → L3:

- потрібна зміна коду;
- виявлено архітектурну проблему;
- потрібна зміна API;
- необхідна міграція даних;
- проблема повторюється після стандартного відновлення.

## 6. Known Issues

### KI-001 — External Service Unavailable

Компонент:

external_service.py

Проблема:

зовнішня залежність на порту 5001 може бути недоступною.

Симптом:

`/tasks/summary` повертає:

- status = degraded;
- source = fallback;
- attempts = 3.

Вплив:

основний API залишається доступним, але latency збільшується.

Workaround:

використовується fallback-механізм.

Необхідно перевірити доступність зовнішнього сервісу та відновити його роботу.

Пов’язаний інцидент:

INC-001.

### KI-002 — Increased Latency During Retry

Проблема:

при недоступності зовнішнього сервісу система виконує три повторні спроби.

Наслідок:

latency може перевищувати цільове значення 300 ms.

Workaround:

перевірити стан зовнішньої залежності та відновити її до завершення retry cycle.

### KI-003 — In-Memory Runtime State

Проблема:

частина runtime-даних системи може зберігатися у пам’яті процесу.

Наслідок:

після перезапуску застосунку можливе очищення runtime-стану.

Workaround:

не використовувати runtime state як довготривале сховище.

Заплановане покращення:

перехід до persistent storage відповідно до RFC-001.

## 7. Пріоритети технічного вдосконалення

### Priority 1 — External Dependency Monitoring

Додати окремий контроль доступності зовнішнього сервісу.

Мета:

виявляти недоступність залежності до того, як вона вплине на користувацький запит.

### Priority 2 — External Service Configuration

Винести URL зовнішньої залежності з коду у конфігурацію або environment variable.

Мета:

спростити deployment у різних середовищах.

### Priority 3 — Improve Retry Strategy

Переглянути retry/backoff policy.

Мета:

зменшити latency у випадку недоступної залежності.

### Priority 4 — Improve Test Coverage

Розширити resilience та mutation tests для external_service.py.

Мета:

зменшити кількість неперевірених граничних сценаріїв.

### Priority 5 — Persistent Storage

Реалізувати persistent storage відповідно до RFC-001.

Мета:

зменшити ризик втрати runtime-даних після restart.

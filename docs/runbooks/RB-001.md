# RB-001 - Відновлення Flask API після недоступності health endpoint

## 1. Ідентифікатор і назва

ID: RB-001

Назва: Відновлення Flask API після недоступності GET /health

## 2. Призначення

Runbook описує дії чергового спеціаліста у випадку, коли Flask API проєкту QualityLab_1 перестає відповідати на health-перевірку.

Основний health endpoint:

GET http://127.0.0.1:5000/health

Нормальна відповідь:

{"status":"ok"}

Очікуваний HTTP-код:

200 OK

## 3. Тригер

Runbook застосовується при спрацюванні одного з таких алертів:

- APIHealthCheckFailed;
- APIPort5000Unavailable;
- APIRepeated5xx.

Основний тригер: health endpoint GET /health двічі поспіль не повертає HTTP 200 або недоступний протягом 1 хвилини.

## 4. Передумови

Черговий спеціаліст повинен мати:

- доступ до macOS-середовища, де розгорнуто QualityLab_1;
- доступ до репозиторію проєкту;
- права на перегляд і завершення локальних процесів;
- встановлений Python 3.12;
- створене віртуальне середовище .venv;
- встановлені залежності проєкту;
- доступ до Terminal.

Робочий каталог:

~/PycharmProjects/QualityLab_1

## 5. Покрокова процедура відновлення

### Крок 1. Перейти до каталогу проєкту

cd ~/PycharmProjects/QualityLab_1

### Крок 2. Активувати Python virtual environment

source .venv/bin/activate

### Крок 3. Перевірити health endpoint

curl -i http://127.0.0.1:5000/health

Нормальний результат:

HTTP/1.1 200 OK

{"status":"ok"}

Якщо endpoint працює, подальше відновлення не потрібне.

### Крок 4. Перевірити, чи порт 5000 зайнятий процесом

lsof -i :5000

Для отримання PID:

lsof -ti :5000

Якщо результат порожній, Flask API не запущений.

### Крок 5. Перевірити стан репозиторію

git status --short

Цей крок потрібний, щоб перед перезапуском переконатися, що в робочій копії немає неочікуваних змін.

### Крок 6. Запустити Flask API

python3 app.py

Очікуваний результат:

Running on http://127.0.0.1:5000

### Крок 7. Якщо порт 5000 зайнятий завислим або некоректним процесом

Спочатку визначити PID:

lsof -ti :5000

Після перевірки PID завершити процес:

kill $(lsof -ti :5000)

Потім повторно запустити API:

python3 app.py

## 6. Верифікація

Після відновлення виконати:

curl -i http://127.0.0.1:5000/health

Критерії успішного відновлення:

- HTTP-код 200;
- тіло відповіді містить "status": "ok";
- порт 5000 прослуховується;
- процес Flask не завершується одразу після запуску.

Додаткова перевірка:

curl -i http://127.0.0.1:5000/api/system/info

Очікується HTTP 200 і службова інформація про QualityLab_1.

## 7. Процедура відкату

Якщо після перезапуску API:

- продовжує повертати помилки;
- health endpoint не проходить перевірку;
- з’являються нові 5xx-відповіді,

необхідно завершити новий процес:

kill $(lsof -ti :5000)

Після цього система повертається до стану до спроби перезапуску.

Не виконувати довільні зміни коду під час чергового відновлення.

Якщо проблема пов’язана зі зміною коду, необхідно перейти до процедури Change Management та RFC, а не виправляти код без документованого рішення.

## 8. Ескалація

### L1 — черговий спеціаліст

Час на первинну діагностику: до 5 хвилин.

L1:

- перевіряє /health;
- перевіряє порт 5000;
- перезапускає Flask API за цим runbook;
- фіксує результат.

### L2 — Developer / SRE

Ескалація до L2 виконується, якщо:

- API не відновився після одного контрольованого перезапуску;
- повторно виникає та сама помилка;
- health endpoint повертає 5xx;
- у логах є exception.

Час ескалації: не пізніше 10 хвилин від початку інциденту.

### L3 — System Architect / Tech Lead

Ескалація до L3 виконується, якщо:

- проблема пов’язана з архітектурою;
- потрібна зміна API-контракту;
- проблема повторюється після виправлення;
- потрібне рішення через RFC або ADR.

## 9. Рівень автоматизації

Рівень автоматизації: 1 — скриптована операція.

Операція виконується набором стандартизованих консольних команд для перевірки процесу, порту та health endpoint.

Повністю автоматичне self-healing не використовується, оскільки поточний навчальний контур QualityLab_1 працює як локальний Flask-застосунок і не має production orchestrator, який автоматично перезапускає сервіс.

Перспективні покращення:

- автоматизований health check;
- автоматичний restart процесу;
- Alert Manager;
- container restart policy.

## 10. Каталог алертів моніторингу

| Назва алерту | Умова спрацювання | Серйозність | Відповідальна роль | Runbook |
|---|---|---|---|---|
| APIHealthCheckFailed | GET /health не повертає HTTP 200 два рази поспіль | Critical | SRE | RB-001 |
| APIPort5000Unavailable | порт 5000 не прослуховується протягом 1 хвилини | High | SRE | RB-001 |
| APIRepeated5xx | частка HTTP 5xx перевищує 5% за 5 хвилин | High | Developer / SRE | RB-001 |

## 11. Зв’язок алертів із runbook

Кожен алерт із каталогу має однозначне посилання на RB-001.

Таким чином виконується правило:

«Алерт без runbook — це шум».

Черговий спеціаліст після отримання алерту не аналізує вихідний код як першу дію, а виконує документовану процедуру RB-001.

## 12. Критерій завершення операції

Операція вважається успішно завершеною, якщо:

- Flask API запущений;
- GET /health повертає HTTP 200;
- відповідь містить "status": "ok";
- порт 5000 доступний;
- повторний health check проходить успішно;
- інцидент не потребує подальшої ескалації.

# RFC-001 — Перехід від In-Memory Storage до SQLite

## 1. Загальна інформація

RFC-ID: RFC-001

Ініціатор: Project Owner

Дата подання: 2026-11-28

Назва зміни: Перехід від in-memory storage до persistent SQLite storage.

Поточний статус: Pending CCB

## 2. Опис зміни

Поточна версія QualityLab_1 зберігає runtime-дані у Python lists та dictionaries.

Після завершення процесу Flask ці дані можуть бути втрачені.

Запропонована зміна передбачає введення SQLite як постійного локального сховища для даних системи.

Існуючі публічні REST API endpoint-и повинні залишитися сумісними.

## 3. Мета зміни

Основні цілі:

- забезпечити збереження даних після перезапуску Flask API;
- зменшити ризик втрати runtime-стану;
- покращити RPO;
- забезпечити можливість резервного копіювання;
- підготувати систему до подальшого production deployment.

## 4. Обґрунтування

Поточний in-memory storage є достатнім для навчального середовища, але не забезпечує persistence.

SQLite дозволить:

- зберігати дані після перезапуску;
- створювати резервні копії;
- виконувати Restore Drill;
- покращити recovery;
- зменшити експлуатаційний ризик.

## 5. Клас зміни за ITIL

Тип зміни: Normal Change.

Зміна не є аварійною та не є типовою стандартною операцією.

Вона зачіпає архітектуру, дані, тестування та експлуатацію, тому повинна пройти Impact Analysis і CCB.

## 6. Клас ризику

Ймовірність збою: 3 із 5.

Наслідки збою: 4 із 5.

# 9. Impact Analysis

## 9.1. Рівень 1 — Вимоги

Зміна поведінки системи:

дані повинні зберігатися після перезапуску застосунку.

Основні API-сценарії для користувача залишаються незмінними.

Нові нефункціональні вимоги:

- persistence;
- recovery;
- backup;
- data integrity.

Необхідно оновити README та експлуатаційну документацію.

Impact: Medium.

## 9.2. Рівень 2 — Архітектура

Поточна схема:

Flask API → In-Memory Storage.

Нова схема:

Flask API → SQLite Database.

Необхідно оновити:

- SDD;
- ISD;
- архітектурну діаграму;
- модель даних;
- ADR щодо способу зберігання даних.

Impact: High.

## 9.3. Рівень 3 — Код

Зміна може зачепити:

- app.py;
- task_service.py;
- privacy_data_service.py;
- consent_service.py;
- requirements.txt;
- модуль persistence;
- автоматичні тести.

Business logic повинна бути відокремлена від persistence layer.

Impact: High.

## 9.4. Рівень 4 — API

Публічні endpoint-и повинні залишитися сумісними.

Основні endpoint-и:

GET /health

GET /api/system/info

GET /tasks/summary

та наявні privacy і consent endpoint-и.

Класифікація API-зміни:

Non-breaking / internal architectural change.

Після реалізації необхідно повторно перевірити openapi.yaml та Spectral.

Impact: Low / Medium.

## 9.5. Рівень 5 — Дані

Необхідно створити SQLite schema.

Дані повинні зберігатися у persistent storage.

Перед міграцією створюється backup.

Міграція повинна бути reversible.

Rollback повинен забезпечувати можливість повернення до попередньої реалізації storage.

Impact: High.

## 9.6. Рівень 6 — Тести

Необхідно повторно запустити:

- pytest;
- health endpoint test;
- system info test;
- task summary test;
- privacy tests;
- consent tests;
- persistence test;
- restart persistence test;
- rollback test.

Основний сценарій:

створення даних → restart API → повторне читання даних.

Impact: High.

## 9.7. Рівень 7 — Документація та експлуатація

Необхідно оновити:

- README.md;
- SDD;
- ISD;
- ADR;
- docs/api/openapi.yaml, якщо зміниться API;
- RB-001;
- backup policy;
- restore drill;
- CHANGELOG;
- slo.yaml за потреби.

Definition of Done з ЛР11 повинна бути виконана.

Impact: High.

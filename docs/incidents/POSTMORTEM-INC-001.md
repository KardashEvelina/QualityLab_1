# Blameless Post-Mortem — INC-001

## 1. Incident

Incident ID: INC-001

Компонент: external_service.py

Дата: 2026-11-28

Severity: SEV-3

## 2. Короткий опис

Під час контрольованого тесту зовнішній сервіс на порту 5001 був недоступний.

Основний Flask API не впав і продовжував повертати HTTP 200, але endpoint /tasks/summary перейшов у degraded mode.

Усі 5 тестових запитів отримали fallback-відповідь.

## 3. Impact

Загальна кількість запитів: 5.

Зачеплених запитів: 5.

Degraded requests: 100%.

HTTP 5xx: 0.

HTTP 200: 5.

Latency становила приблизно 616–622 ms.

Цільове значення latency було менше 300 ms, тому під час інциденту latency objective не виконувалась.

## 4. Evidence

Основний лог:

lab12_results/incident_fail.log

FAIL commit:

4a8e6aa — ops(incident): capture legacy module outage, FAIL

У логах зафіксовано:

- Connection refused;
- зовнішній сервіс :5001 недоступний;
- 3 повторні спроби;
- fallback response;
- degraded = true;
- latency більше 300 ms.

## 5. Blameless Principle

Ми не шукаємо винну людину.

Ми шукаємо, яка частина системи або процесу дозволила проблемі виникнути.

# 6. RCA — 5 Чому

## Чому 1

Чому система перейшла у degraded mode?

Тому що external_service.py не зміг отримати відповідь від зовнішнього сервісу.

Доказ:

У логах є повідомлення Connection refused та External service is unavailable.

## Чому 2

Чому external_service.py не зміг отримати відповідь?

Тому що на порту 5001 не працював зовнішній сервіс.

Доказ:

Перевірка порту показала:

PASS: external dependency on port 5001 is DOWN.

## Чому 3

Чому недоступність зовнішнього сервісу вплинула на /tasks/summary?

Тому що endpoint /tasks/summary використовує get_external_status(), який звертається до цього зовнішнього сервісу.

Доказ:

У коді app.py endpoint /tasks/summary викликає get_external_status().

## Чому 4

Чому кожен запит став повільнішим?

Тому що перед fallback система виконувала три спроби звернення до недоступного сервісу та чекала між повторними спробами.

Доказ:

Для кожного тестового запиту:

attempts = 3.

Latency була приблизно 616–622 ms.

## Чому 5

Чому проблема могла існувати до моменту виконання запиту користувача?

Тому що для цієї зовнішньої залежності не було окремого операційного контролю, який завчасно повідомляв би про її недоступність.

Проблема ставала видимою вже тоді, коли система намагалася використати зовнішній сервіс.

Доказ:

Інцидент був виявлений під час активного запиту до /tasks/summary і перевірки порту 5001.

## Root Cause

Коренева причина полягає не в діях конкретної людини, а в недостатньому операційному контролі зовнішньої залежності.

Система мала retry та fallback, але не мала окремого механізму раннього виявлення недоступності зовнішнього сервісу до виконання користувацького запиту.

Через це збій не призвів до повного падіння API, але викликав degraded mode та збільшення latency.

## Люди та навчання

Можлива проблема:

команда може не одразу знати, що зовнішній сервіс на порту 5001 є важливою залежністю.

Рішення:

описати залежність у документації та runbook.

## Процеси та регламенти

Можлива проблема:

не було окремої регулярної перевірки доступності зовнішнього сервісу.

Рішення:

додати перевірку зовнішньої залежності до операційного регламенту.

## Технології та інструменти

Можлива проблема:

система має retry та fallback, але відсутній окремий автоматичний health check зовнішньої залежності.

Рішення:

додати health probe або monitoring check для сервісу :5001.

## Дані

Під час цього інциденту втрати або пошкодження даних не було зафіксовано.

Ця категорія не є основною причиною інциденту.

## Середовище

Зовнішній сервіс працює окремо на порту 5001.

Якщо процес цього сервісу не запущений, основний застосунок не може отримати від нього відповідь.

## Моніторинг

Можлива проблема:

відсутній окремий alert на недоступність external service.

Через це проблема виявляється вже під час виконання запиту.

# 8. Висновок RCA

Основний Flask API залишився доступним завдяки fallback-механізму.

Проте недоступність зовнішнього сервісу призвела до:

- 100% degraded responses у контрольному тесті;
- трьох retry на кожен запит;
- збільшення latency приблизно до 620 ms;
- перевищення latency objective.

Коренева проблема має системний характер:

недостатній моніторинг та операційний контроль зовнішньої залежності.

Людина не визначається як причина інциденту.
